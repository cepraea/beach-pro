## 2. Problema observado

O desenvolvimento do CEPRAEA BEACH PRO apresenta episódios recorrentes nos quais uma tarefa de produto ou de arquitetura é interrompida e o esforço passa a ser consumido por recuperação do próprio ambiente/processo de desenvolvimento.

Os episódios recuperados até a abertura deste registro incluem quatro classes principais:

1. **estado Git/branch/baseline divergente ou difícil de determinar;**
2. **handoff mecânico e operação Git manual entre Executor, Reviewer e humano;**
3. **ciclos de alteração protegida → rebuild do DevContainer → revalidação → nova correção;**
4. **retrabalho epistemológico quando uma análise/orientação é tratada como verificada sem evidência suficiente.**

Não está demonstrado que essas quatro classes tenham uma única causa raiz. Neste registro elas são tratadas como clusters de sintomas e control gaps até a RCA produzir evidência suficiente.

## 8. Clusters causais em investigação

Os itens abaixo são **hipóteses de RCA**, não root causes aprovadas.

### CH-01 — Repository state não é gateado antes de iniciar nova tarefa

Sinais:

- branch antiga permaneceu ativa após evolução do `main`;
- working tree dirty coexistiu com mudança de arquitetura;
- `main` local ficou 47 commits atrás;
- o operador precisou descobrir o estado por sequência manual de comandos.

Hipótese: ausência de um preflight simples e obrigatório aumenta a probabilidade de iniciar trabalho em baseline inadequado.

### CH-02 — Controle crítico depende de intervenção humana mecânica

Sinais:

- arquivos protegidos são corretamente read-only para os agentes;
- alterações neles dependem de Davi;
- rebuild também depende de Davi;
- validação volta ao agente após rebuild.

Hipótese: a fronteira de segurança está correta, mas o workflow de materialização/validação não minimiza o trabalho mecânico humano.

### CH-03 — Handoff entre Executor e Reviewer é parcialmente manual

Sinal: Davi relatou copiar handoff do Executor para o Codex e se perder em branches/commits/diffs.

Hipótese: o humano está exercendo simultaneamente autoridade, barramento de mensagens e operador Git.

### CH-04 — Claims analíticas podem adquirir autoridade antes de verificação

Sinal: episódio de 08/08 em que uma “verificação” foi posteriormente reconhecida como sem consulta suficiente às fontes.

Hipótese: ausência de contrato `CLAIM → EVIDENCE → VERDICT` em algumas etapas gera retrabalho arquitetural.

### CH-05 — Custo de mudança do DevContainer é alto para experimentação iterativa

Sinais:

- control-plane é copiado para a imagem;
- mudanças exigem rebuild para chegar ao runtime;
- testes de sandbox demonstraram diferença entre arquivo no repo e configuração efetivamente carregada.

Hipótese: mudanças pequenas de configuração possuem feedback loop muito maior que mudanças normais de código.

## 10. Ações do Problem Record

### PRB-ACT-001 — Preflight determinístico de início de sessão

Verificar antes de nova TASK:

```text
repository root
current branch
HEAD
origin/main
working tree
branch relationship to origin/main
```

O objetivo é detectar estado inesperado **antes** de começar implementação.

### PRB-ACT-002 — Procedimento de encerramento de TASK

Definir e validar sequência mínima:

```text
Review PASS
→ Human Git Operator
→ squash/merge
→ sincronizar main local
→ working tree conhecido
→ encerrar TASK
```

### PRB-ACT-003 — Medir rebuild automaticamente

Registrar por rebuild:

```text
rebuild_started_at
rebuild_completed_at
rebuild_seconds
reason
changed_control_plane_paths
result
```

O baseline humano previamente reportado de aproximadamente 4 minutos deve ser substituído por medição automática.

### PRB-ACT-004 — Reduzir handoff mecânico

O humano deve continuar como autoridade, mas não como barramento manual de texto entre Executor e Reviewer.

Critério: uma revisão deve conseguir recuperar TASK, contrato, diff e evidência do repositório/artefatos sem depender de copy/paste de um handoff narrativo completo.

### PRB-ACT-005 — Contract de evidência para análises

Nenhum resultado material de análise/auditoria pode ser promovido a fato verificado somente porque um agente o afirmou.

Aplicar:

```text
CLAIM
→ SOURCE
→ EVIDENCE
→ REPRODUCTION/METHOD quando aplicável
→ VERDICT
```

### PRB-ACT-006 — Separar recuperação de hardening

Uma correção de incidente não deve automaticamente crescer para uma reengenharia ampla do SDLC.

Cada novo mecanismo precisa apontar:

```text
incident/problem evidence
→ failure mode
→ control
→ acceptance test
```

### PRB-ACT-007 — Criar registro temporal de sessões

Sem telemetria mínima de tempo, o custo sistêmico continuará sendo percebido, mas não mensurado.

O objetivo é produzir a primeira série confiável de:

- tempo de produto;
- tempo de recuperação;
- tempo de rebuild;
- tempo de handoff;
- retrabalho.

## 11. Critérios para considerar o problema controlado

`PRB-SDLC-20260819-001` não pode ser fechado apenas porque o incidente de 19/08 foi resolvido.

O status pode mudar de `OPEN` para `CONTROLLED` somente quando houver evidência de que:

- início de TASK detecta baseline/branch/dirty tree incompatíveis antes de implementação;
- encerramento de TASK deixa `main` local em estado conhecido;
- rebuild possui duração e causa registradas automaticamente;
- handoff manual de texto não é necessário para revisão normal;
- análises materiais seguem `CLAIM → EVIDENCE → VERDICT`;
- pelo menos uma janela de medição produz `RECOVERY_LOAD_RATIO` com denominador válido;
- nenhum controle introduzido exige enfraquecer a proteção de dados pessoais ou o control-plane.

O status `CLOSED` exige ainda uma janela posterior sem recorrência relevante ou decisão humana explícita de aceitar o risco residual. A duração dessa janela permanece `PENDING_HUMAN_DECISION`.
